Retrieval-Augmented Generation

4 questions
01

Design a policy assistant

A client has 200 PDFs, some scanned, and updates policies monthly. Employees need answers with citations. Start with a simple design and explain how you would prove it works.

Reveal step-by-step answer
  1. Ask who can see which policies, how quickly updates must appear, and what counts as a valid citation. Agree that absent or conflicting evidence triggers an abstention or clarification.
  2. Extract text, OCR scans, and check page/table quality. Split at headings and preserve policy ID, version, effective date, page, and access metadata. Use overlap only where boundaries otherwise cut meaning.
  3. Embed chunks, index the vectors plus metadata, and embed queries with the same model. Filter by access and effective date, retrieve top candidates, and give the model a bounded set of excerpts with source IDs.
  4. Verify that citations refer to supplied excerpts. Test paraphrases, exact policy IDs, tables, update visibility, and queries with no answer. Measure retrieval before judging the prose.
Interviewer follow-up

A revised PDF arrives during indexing.

Reveal follow-up answer

Build a complete version separately, check it, atomically switch the active version, and retire the old one from current-policy retrieval. Keep version history only where authorized and useful.

02

Find the source of the stale answer

A) The correct policy was never indexed. B) It was indexed but missed by retrieval. C) It reached the prompt but the answer still cited the old rule. How would you tell these apart?

Reveal step-by-step answer
  1. Freeze the query and capture redacted identifiers for the policy version, candidate list, final context, and output citation. Determine the expected policy and effective date from the source of record.
  2. Check the active index metadata and the access filter. A missing version is an ingestion problem; a current chunk excluded by a wrong filter is a retrieval configuration problem.
  3. If it is indexed, inspect candidate rank and the text after reranking and truncation. Compare top-k recall on labeled questions. If the passage survived in the prompt, rerun with only the correct evidence to isolate generation or competing evidence.
  4. Add a regression for the failing layer. Fix that layer first and rerun the same query plus neighboring date and permission cases.
Interviewer follow-up

Why not increase top-k immediately?

Reveal follow-up answer

It can improve recall but also add obsolete or irrelevant text and increase cost; inspect the correct passage’s rank and validate the change against a fixed set.

Fix chunk boundaries and exact-match misses

A benefit rule names a threshold in a table and its exception in the next paragraph. Semantic search misses policy code AB-417. What would you change?

Reveal step-by-step answer
  1. Inspect parsed text first: preserve table headers, rows, units and the nearby exception; a text splitter cannot restore text the parser dropped.
  2. Index small child chunks for matching and keep a pointer to their parent section. Retrieve a matching child, then supply enough neighboring context to include the exception.
  3. Add keyword retrieval for codes and names alongside vectors for paraphrases. Combine rankings, deduplicate, and rerank if needed. Keep access metadata on every candidate.
  4. Compare the old and new setup on exact codes, cross-paragraph exceptions and paraphrases. Check recall, answer correctness, and tokens per query.
Interviewer follow-up

What if a vector score is 0.91?

Reveal follow-up answer

Treat it as a ranking signal under that model and metric. Check relevance and citation support; the number is not a probability that an answer is true.

Retrieve across restricted document sets

HR and finance share an assistant, but each employee must see only approved policies. Where does access control live, and what happens when access is revoked?

Reveal step-by-step answer
  1. Authenticate outside the model; use identity and permissions from the trusted application session. Define document-level access in the source metadata.
  2. Apply authorization in retrieval before placing any text in model context. Scope caches to the relevant identity or permission set, index version and query; invalidate on permission changes.
  3. Recheck authorization when opening a citation. Keep raw text out of general traces; record opaque document IDs and the decision where authorized.
  4. Test explicit allowed and denied users, mixed permissions and revocation, including warm-cache cases. A user must not get forbidden content even if they ask for it explicitly.

Can I redact after generation?

Reveal follow-up answer

That is a secondary control. Once the text entered the prompt, it has already crossed the retrieval boundary and can influence or leak into the answer.

RAG vs. fine-tuning

4 questions
01

Choose the smallest useful technique

The client says, “Fine-tune the model on our HR policies.” Policies change monthly and users need a citation for each benefit. What do you propose?

Reveal step-by-step answer
  1. Separate fresh knowledge, traceability, and response behavior. Monthly changes and source links are evidence requirements.
  2. Start with retrieval over effective, authorized policy versions. Use a simple prompt that asks for cited answers and says when to abstain.
  3. Test a prompt-only baseline on representative requests and compare the RAG version on currentness, citation support, latency, and errors. Tag misses by evidence versus behavior.
  4. Consider fine-tuning only for a recurring behavior problem that good prompts and schemas leave unresolved. Retain retrieval for policy facts.
Interviewer follow-up

Can training data replace the citations?

Reveal follow-up answer

No reliable citation follows from putting text in training. Use a traceable current source and verify the quoted or paraphrased claim against it.

Fix a stable style or format problem

The right evidence is already in context, but support replies keep breaking a fixed schema or adopting the wrong tone. When would you try training?

Reveal step-by-step answer
  1. Separate machine-readable format from tone. Use constrained or schema-guided output if supported, then validate structure and business values in code.
  2. Improve instructions and examples using an explicit missing-data case. Compare with a deterministic template for fields that do not need free text.
  3. If tone or task behavior still fails systematically at scale, assemble labeled, permitted demonstrations and hold out distinct examples before training an adapter.
  4. Compare the tuned and baseline models on the same held-out behavior, grounding, and latency checks. Keep the cheaper baseline if gains do not justify operating a tuned model.

Does schema-valid output mean the issue is solved?

Reveal follow-up answer

It proves specified structure and types. Verify field semantics, evidence, and permissions separately.

Defend a combined design

An insurer wants citations to frequently updated policies and consistent triage labels. Design a baseline before proposing RAG plus tuning.

Reveal step-by-step answer
  1. Write two acceptance tests: a user can open each supporting policy clause, and labels follow a reviewed taxonomy.
  2. Retrieve evidence by policy and date; require citation IDs in the response. Start with examples for the labels and an explicit unknown category.

What goes in the training set?

Approved examples of desired behavior, reviewed labels and edge cases. Hold out comparable but distinct cases and avoid relying on changing policy facts as label shortcuts.

Diagnose the apparent fine-tuning win

A fine-tuned model scores 92% on a worksheet copied from historical tickets. The old model got 84%, but the production errors concern newly written tickets. What do you trust?

Reveal step-by-step answer
  1. Ask how the worksheet was sampled and whether examples or near-duplicates were used for training or prompt design.
  2. Create a time-separated, deduplicated evaluation set drawn from the intended production queue, and define pass criteria before scoring.

Tool-using agents

4 questions
01

Trace an actual Sandbox tool call

Walk me through the implementation from the model requesting a tool to receiving a result. Where is the state, and what did the saved tests actually establish?

Reveal step-by-step answer
  1. A conversation turn invokes the graph with a thread ID. The model receives messages and structured tool schemas; a requested tool is an action proposal rather than executed Python.
  2. The graph routes the tool call to the adapter and dispatch implementation. Container-backed execution returns observations, which become tool messages for the model’s next turn. Some browser actions are host-side, so do not describe everything as container-contained.
  3. The graph keeps per-thread checkpoint state in memory. Explain intended step and retry bounds, then qualify them: the audited state schema lacks retry_count and the max reducer does not reset a reused thread’s count.
  4. Cite the saved 12/14 integration result, and treat it as test evidence for those cases, not proof of an isolation or retry guarantee.
Interviewer follow-up

Why mention logical state and enforcement separately?

Reveal follow-up answer

A constant or field written by a node does not enforce a budget unless it survives state updates and is checked at every route that can perform work.

Pick a workflow or agent

Every request must be validated, looked up, summarized, and reviewed. A stakeholder wants an agent because it sounds more flexible. What do you build?

Reveal step-by-step answer

03

A tool times out after a write

An agent calls an internal ticket creation tool. It receives a timeout and asks to call it again. How do you avoid creating duplicate tickets?

Reveal step-by-step answer
  1. Treat timeout as unknown outcome. Distinguish a transport failure from a clear validation error or known successful write.
  2. Use a stable request key and enforce a durable uniqueness contract on the server; a model-generated retry count cannot make a write idempotent.
  3. On timeout, reconcile via status lookup or retry the same key under a bounded policy when the tool contract allows it. Escalate unknown outcomes rather than issuing a fresh key.
  4. Test timeouts before and after commit and duplicated delivery; assert one durable ticket and an accurate status in the user response.
Interviewer follow-up

What can be retried freely?

Reveal follow-up answer

A side-effect-free read can usually be retried for transient errors within a deadline. Do not retry permanent errors or unbounded requests.

Design a reliable tool boundary

You are giving a support assistant read access to ticket status. What are the tool contract, stopping rules, and tests?

Reveal step-by-step answer
  1. Define a narrow tool with typed ticket ID, a small result, explicit errors and a deadline. Derive the caller identity from application context.
  2. Validate input and check authorization at execution time; return typed results or a redacted error instead of verbose internal logs.
  3. Stop on a final answer, repeated identical proposals, max steps, or a deadline. Return a clear partial result or escalation path when the run cannot finish.
  4. Test malformed IDs, unauthorized tickets, missing results, transient errors and repeated requests. Assert outcomes and tool calls, not just conversational wording.

The API returned a note that asks the model to do another task.

Treat the note as ticket data. It cannot expand the available tools or authorize another action.

4 questions
01

Budget a long conversation

Assume a model has a combined 8,000-token window. System instructions, recent turns and retrieved chunks already use 7,600 tokens; you need up to 800 tokens for the answer. What do you change?

Reveal step-by-step answer
  1. Count tokens with the target tokenizer and include message wrappers and tool schemas where applicable. The requested total is 8,400, so remove at least 400 input tokens plus headroom.
  2. Preserve trusted rules and relevant recent instructions. Drop duplicate passages, compress older discussion into a reviewed summary, and retrieve only evidence relevant to the current question.
  3. Reserve the answer budget before assembling the prompt. Record what was truncated, and test long conversations with a key constraint near the beginning.
  4. Keep temperature separate: it changes token selection among available possibilities and cannot restore omitted context.
Interviewer follow-up

What if the request still cannot fit?

Reveal follow-up answer

Ask for a narrower question or process the material in bounded steps with traceable intermediate results instead of silently dropping a requirement.

02

Temperature versus top-p

The same extraction prompt produces three different outputs. Explain temperature and top-p using a simple example; then say how you would fix the feature.

Reveal step-by-step answer
  1. Temperature rescales logits before sampling: lower positive values sharpen the distribution; a greedy mode picks the highest-scoring token where supported.
  2. Top-p restricts sampling to a probability-ranked set whose cumulative mass reaches a threshold. With probabilities 0.60, 0.25 and 0.15, top-p 0.80 retains the first two, then renormalizes.
  3. For extraction, use low randomness, a schema, explicit null behavior and source validation. Do not rely on identical decoding to make a field correct.
  4. Hold the model and prompt fixed and score repeated runs on a labeled set. Report field accuracy and invalid-output rate separately.
Interviewer follow-up

Does temperature zero guarantee exact reproducibility?

Reveal follow-up answer

It usually selects greedy decoding if the API defines it that way; provider changes, numerical effects or different implementation details can still change outputs.

03

Explain what an embedding measures

A search for “return policy” finds “refund rules” and a spam page that overuses similar words. What is the vector doing, and how do you correct results?

Reveal step-by-step answer
  1. An embedding maps text to coordinates learned by a model. Nearby points are often semantically similar under the scoring metric, but closeness neither proves relevance nor factual support.
  2. Use the same query and document encoder configuration, or the documented compatible pair. Cosine compares direction; dot product also reflects magnitude unless normalized.
  3. Label a small set with relevant and irrelevant passages. Inspect rankings for exact IDs, similar but wrong products, boilerplate and paraphrases.
  4. Try metadata filters, keyword matching or reranking and evaluate recall@k plus precision near the top. Keep the version with a measurable improvement.
Interviewer follow-up

Can I compare arrays from different embedding models?

Reveal follow-up answer

Equal dimensionality does not mean aligned vector spaces. Re-embed consistently unless the models explicitly define a compatible space.

04

Debug cost and truncation

A prompt that is short in English is far longer for generated SQL and code. Some answers finish mid-object. How do you debug it?

Reveal step-by-step answer
  1. Inspect actual input/output token counts and finish reason. Characters and words are poor proxies, especially for code, punctuation and different languages.
  2. Distinguish output-cap truncation from input overflow and from invalid JSON on a completed run.
  3. Reduce irrelevant input, reserve output tokens, constrain the response shape and handle incomplete responses explicitly before parsing or writing state.
  4. Track token and latency distributions by task type, and set thresholds based on the long tail rather than an average alone.
Interviewer follow-up

Why not raise the output cap for everyone?

Reveal follow-up answer

It can increase latency and cost and does not fix broken formats or overflowing inputs. Change it only where the observed failure warrants it.

Prompting and model judgment

4 questions
01

Stop inventing invoice totals

The extractor returns schema-valid JSON but fills in a total even when the document has none. Design a prompt, validation and fallback for the missing-data path.

Reveal step-by-step answer
  1. Give explicit definitions for total, subtotal, tax and currency. Specify that an absent or ambiguous total is null, and require a source span for each non-null value.
  2. Supply examples for present, missing and ambiguous totals. Use synthetic values distinct from real invoices, and tell the model not to treat examples as evidence.
  3. Validate types, source span, currency and amount with deterministic code. If business policy permits computing totals, put the calculation in a separate verified path and label it computed.
  4. On missing evidence, preserve null; on invalid or conflicting output, route to review. Track exact field accuracy and unsupported non-null values.
Interviewer follow-up

What if the invoice clearly says USD 0.00?

Reveal follow-up answer

Zero with supporting text is a valid amount. Null means missing or unresolved; test the two cases separately.

4 questions
01

Treat a retrieved instruction as data

A policy excerpt contains text asking the assistant to share internal files. How do you prevent the model’s interpretation from turning into an action?

Reveal step-by-step answer
  1. Classify the retrieved excerpt as untrusted evidence. It cannot set policy, grant permission, or expand the user’s requested task.
  2. Use an allowlist and a server-side authorization check for each tool request. A read-only policy assistant has no outbound file-sharing capability.
  3. Keep prompts limited to authorized data; isolate external actions behind a separate explicit user intent and deterministic permission checks where applicable.
  4. Test the case with clearly marked synthetic text. Assert absence of disallowed tool requests being executed and check the resulting response and trace without copying document contents.
Interviewer follow-up

Is “ignore injections” in the prompt enough?

Reveal follow-up answer

No. It can guide behavior, but runtime controls must reject a forbidden action even if the model proposes it.

Reveal step-by-step answer
  1. Confirm the timestamp representation and what to do with missing fields. Assume validated, timezone-normalized timestamps and comparable IDs for the pure function.
  2. Make one pass. Keep a dictionary from customer ID to the best record seen so far; replace it only when the candidate’s tuple compares greater.
  3. Explain the invariant after each iteration: every key maps to the maximum tuple in the prefix already seen. Expected O(n) time and O(u) extra space for u customers.
  4. Test empty input, interleaved customers, a timestamp tie, out-of-order input and no mutation. Keep network parsing and retry tests separate.

Worked solution · Python

def latest_by_customer(records):
    """Keep the maximum (timestamp, record_id) per customer."""
    latest = {}
    for row in records:
        customer = row["customer_id"]
        candidate = (row["timestamp"], row["record_id"])
        if customer not in latest:
            latest[customer] = row
        else:
            current = latest[customer]
            if candidate > (current["timestamp"], current["record_id"]):
                latest[customer] = row
    return latest

Latest accepted submission per bounty

Tables are bounty(id) and submission(id, bounty_id, status, submitted_at). Return one row for every bounty, with its latest accepted submission if any. Break ties by larger submission ID. Assume submitted_at is non-null.

Reveal step-by-step answer
  1. Apply status = accepted before ranking, so a later rejected submission cannot hide an earlier accepted one.
  2. Use ROW_NUMBER partitioned by bounty_id and ordered by submitted_at descending, then id descending.
  3. Left join the ranked rows to bounty and put rank = 1 in the ON clause. Bounties with no eligible submission should retain null submission columns.
  4. Test no submissions, only rejected, later rejected, and equal timestamps. Compare row count to distinct bounty count.

Worked solution · SQL

WITH ranked AS (
    SELECT id, bounty_id, submitted_at,
           ROW_NUMBER() OVER (
               PARTITION BY bounty_id
               ORDER BY submitted_at DESC, id DESC
           ) AS rn
    FROM submission
    WHERE status = 'accepted'
)
SELECT b.id AS bounty_id, r.id AS submission_id, r.submitted_at
FROM bounty AS b
LEFT JOIN ranked AS r
    ON r.bounty_id = b.id AND r.rn = 1
ORDER BY b.id;

Trace the next token

Reveal step-by-step answer
  1. Tokenize the text into IDs, then map IDs to vectors and incorporate positional information.
  2. Each causal self-attention head makes queries, keys and values from the current representations. Attention scores and mixes values from allowed earlier positions; a causal mask blocks future positions.
  3. Feed-forward layers further transform each position; residual paths and normalization help stacked blocks process the representation. The output projection produces vocabulary logits for the next token.
  4. The decoding rule picks a token from those logits. Append it and repeat until a stop condition; ordinary inference does not change the model’s weights.

It is a routing coefficient inside the model. It does not by itself establish factual evidence or a complete explanation of the final decision.

Code latest record per customer

Reveal step-by-step answer
  1. Confirm the timestamp representation and what to do with missing fields. Assume validated, timezone-normalized timestamps and comparable IDs for the pure function.
  2. Make one pass. Keep a dictionary from customer ID to the best record seen so far; replace it only when the candidate’s tuple compares greater.
  3. Explain the invariant after each iteration: every key maps to the maximum tuple in the prefix already seen. Expected O(n) time and O(u) extra space for u customers.
  4. Test empty input, interleaved customers, a timestamp tie, out-of-order input and no mutation. Keep network parsing and retry tests separate.

Worked solution · Python

def latest_by_customer(records):
    """Keep the maximum (timestamp, record_id) per customer."""
    latest = {}
    for row in records:
        customer = row["customer_id"]
        candidate = (row["timestamp"], row["record_id"])
        if customer not in latest:
            latest[customer] = row
        else:
            current = latest[customer]
            if candidate > (current["timestamp"], current["record_id"]):
                latest[customer] = row
    return latest

Latest accepted submission per bounty

Reveal step-by-step answer

  2. Use ROW_NUMBER partitioned by bounty_id and ordered by submitted_at descending, then id descending.
  3. Left join the ranked rows to bounty and put rank = 1 in the ON clause. Bounties with no eligible submission should retain null submission columns.
  4. Test no submissions, only rejected, later rejected, and equal timestamps. Compare row count to distinct bounty count.

Worked solution · SQL

WITH ranked AS (
    SELECT id, bounty_id, submitted_at,
           ROW_NUMBER() OVER (
               PARTITION BY bounty_id
               ORDER BY submitted_at DESC, id DESC
           ) AS rn
    FROM submission
    WHERE status = 'accepted'
)
SELECT b.id AS bounty_id, r.id AS submission_id, r.submitted_at
FROM bounty AS b

Trade demo scope for reliable value

Two days before a demo, the client asks for three document types. Only one passes the tests. Explain your recommendation directly to the client.

Reveal step-by-step answer
  1. Confirm the demo objective and priority users; find out if the new types are essential to the decision or can be previewed later.

  3. Recommend a live demo for the tested type with a clear scope, and a separately labeled prototype or roadmap for the other types. Agree who can approve new coverage.
