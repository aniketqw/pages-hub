QUESTION
How do you validate the VLM's output? The resume says Pydantic - show me.

WHY THIS QUESTION MATTERS
This is the direct resume-vs-code confrontation question. The interviewer has likely skimmed the repo and wants to see whether the candidate confesses the gap crisply and pivots to a competent fix, or improvises a defense of code that does not exist.

CONTEXT
Format tolerance and structured validation solve different failure modes. The section parser can preserve an answer even when headings are missing, but it does not enforce field types, required values, or semantic correctness. A typed contract should distinguish valid structured output from a raw fallback, and quality monitoring should track both format failures and unsupported diagnoses.

TERMS
Pydantic validation: declaring a typed schema and rejecting/raising on non-conforming data - converts 'the model replied weirdly' into a catchable, retryable error
guided decoding: constraining the LLM's token sampling to a grammar or JSON schema at generation time (supported by vLLM), preventing malformed output rather than parsing around it
_raw fallback: this pipeline's terminal safety net: unstructured VLM output is stored whole under one key so nothing is lost, at the cost of silent structure loss
format drift: a model/prompt change altering output shape so parsers quietly fail more often - detectable only if the fallback rate is measured

MECHANISM
1. Define the seven output fields and value constraints in a typed model, including how uncertain or missing evidence is represented.
2. Use constrained decoding when available, then validate the parsed response and retain raw text plus validation errors on failure.
3. Track parse success and factual grounding separately; a schema-valid response can still make an unsupported claim.

TECHNICAL EXPLANATION
The actual mechanism (pipe/vision_reasoning_report.py L367-407): a fixed list of seven section keys; line-by-line scan; a line whose uppercase form starts with 'KEY:' closes the previous section and opens a new one, capturing any same-line trailing text; unmatched leading content and fully-unstructured replies fall into _raw. Strengths: zero dependencies, tolerant of case variation, never throws, never loses model output. Weaknesses: no schema - a missing ROOT CAUSE section is silently absent rather than an error; no type constraints - CONFIDENCE ASSESSMENT is free text, not a bounded score; no detection of section-order anomalies or duplicated headings (later duplicate overwrites earlier); and crucially no feedback loop - a malformed response is stored as-is rather than retried. The production design I would ship: (1) define a Pydantic model - seven typed fields, confidence as a constrained enum or float; (2) request structured output: vLLM supports guided decoding / JSON schema enforcement, which eliminates most parse failures at the decode level rather than post hoc; (3) validate; on ValidationError, retry once with the error message appended to the prompt; (4) after N failures, store under _raw with a validation_failed flag so downstream consumers can filter; (5) log the validation failure rate as a pipeline health metric - that single number tells you when a model upgrade silently changed output format. The hardcoded recommendations table (L652-662) is the sibling issue: template content presented adjacent to model content; the fix is computing the table from the run's actual distribution and visually distinguishing generated from static text.

WORKED EXAMPLE
A concrete failure the parser tolerates today: if Qwen replies with markdown bold headers like '**ROOT CAUSE**:' instead of 'ROOT CAUSE:', startswith fails, every section misses, and the whole analysis lands in _raw - the report still renders, but the per-section layout silently collapses. A Pydantic-plus-guided-decoding path would have either prevented or loudly flagged that.

def parse_vlm_sections(raw: str) -> Dict[str, str]:
    """
    Parse the VLM response into a dict keyed by section label.
    Expects lines starting with 'LABEL:' as section boundaries.
    Falls back to storing everything under '_raw' if no sections found.
    """
    section_keys = [
        "DISTORTION ARTIFACTS",
        "SURVIVING TRUE-CLASS FEATURES",
        "WHAT MISLED THE MODEL",
        "MODEL REASONING CORRECT",
        "MODEL REASONING INCORRECT",
        "CONFIDENCE ASSESSMENT",
        "ROOT CAUSE",
    ]
    result: Dict[str, str] = {}
    current_key = None
    current_lines: List[str] = []

    for line in raw.splitlines():
        matched = False
        for key in section_keys:
            if line.upper().startswith(key + ":"):
                if current_key:
                    result[current_key] = " ".join(current_lines).strip()
                current_key = key
                # grab any text after the colon on the same line
                after = line[len(key) + 1:].strip()
                current_lines = [after] if after else []
                matched = True

Here is the parser whose existence answers the question. The seven section keys are a hardcoded list. The loop walks raw.splitlines(); the line.upper().startswith(key + ':') check is the entire format contract with the model. When a new key matches, the previous section's lines are joined and stored, and any text after the colon on the same line seeds the new section. Below this slice, leftover lines flush into the final section, and if result is empty everything goes under '_raw'. It is honest, defensive string parsing - and it is not schema validation, which is exactly the resume gap.

LIMIT
The direct risk is the credibility hit of a resume claim the code cannot back - which is why I lead with the confession. The technical risk is silent format drift: nothing in the pipeline alerts me if the fraction of _raw fallbacks jumps after a model or prompt change, so report quality can degrade for weeks unnoticed. Both risks have the same root: no validation contract and no metric on it.

SPEAKABLE ANSWER
I will answer this the way I would in front of a client: the resume says Pydantic-validated output; this pinned pipeline uses a section parser, so I cannot demonstrate that claim from this checkout. What actually runs is parse_vlm_sections in pipe/vision_reasoning_report.py: it scans the VLM's text for seven labeled headings - DISTORTION ARTIFACTS, ROOT CAUSE, CONFIDENCE ASSESSMENT and four more - splits the response on those boundaries, and if no headings match at all it dumps everything under a _raw key so no output is ever lost. That fallback is the one real guardrail: the report degrades gracefully instead of crashing on a malformed reply. The fix I would ship is concrete: a Pydantic model with the seven fields, JSON mode or constrained decoding on the vLLM side so Qwen emits parseable structure, a retry-on-validation-failure loop with the temperature already at 0.1, and the _raw fallback retained as the terminal safety net. There is a second gap in the same file: render_report's 'Actionable Recommendations' table is hardcoded Markdown - including the 'Blur (40%)' cell - so not every recommendation in the report is Qwen-generated, and I say that unprompted.

FOLLOW-UP QUESTIONS AND ANSWERS

1. Why did you write a parser instead of just requesting JSON?
At build time I prioritized robustness over structure: free-text section output with a tolerant parser never hard-fails, whereas naive 'reply in JSON' prompting without enforcement produced occasional truncated or fenced JSON that json.loads rejects. The mature answer is vLLM's guided decoding, which gives schema-conformant output at the decoder level - I simply had not wired it in at this snapshot, and it is the first fix I would ship.

1.1. Why not just prompt for JSON and call json.loads?
Prompting alone does not enforce a schema; the model can return fences, omit fields, or truncate output. The current section parser tolerates format drift but cannot validate types or required values. Guided decoding or a structured response format should enforce syntax, and Pydantic should validate semantics after parsing. I would keep the raw text for diagnosis rather than silently accepting malformed structure.

1.1.1. What is the fallback if schema validation still fails?
Return an explicitly flagged raw response with validation errors and the model/config identifiers, and prevent it from being counted as a structured diagnosis. A bounded repair attempt may help, but repeated retries should stop. The reviewer should be able to tell a successful structured answer from a readable but unvalidated fallback.

2. Is a fallback that hides failure actually a guardrail?
Half of one. Losing no data is genuinely valuable - a human can still read _raw content in the report. What is missing is observability: the fallback should also increment a counter and flag the record, so a rising _raw rate pages someone. A guardrail that catches errors but never reports catching them becomes a place where quality quietly leaks.

2.1. Which metric would reveal a parser regression?
Track structured-parse success rate, raw-fallback rate, missing-field rate, and validation error categories by prompt and model version. Sample records for review when those rates move. A rising raw rate should block publication or require acknowledgement, depending on impact; simply preserving text avoids data loss but does not tell operators that structure failed.

2.1.1. How would you prevent the monitor from hiding bad answers with a high success rate?
Pair format metrics with task-level review: a valid schema can contain unsupported claims. Use a labeled set to score factual grounding and completeness, and keep provenance to the source images and run. Schema validity is a necessary contract check, not evidence that the VLM’s diagnosis is correct.

3. What goes in the retry prompt?
The original request plus two additions: the model's failed output and the specific Pydantic validation errors - 'confidence must be one of low/medium/high' - as explicit correction instructions. One retry recovers most format failures; beyond two, retries mostly burn tokens, so I would cap at two and route to the flagged _raw path. Temperature stays at 0.1 since format compliance is not a creativity problem.

3.1. How do you keep a repair retry from hiding the original parsing failure?
Preserve a sanitized original response reference, validation error and attempt count alongside the repaired result. A successful second response should not make the initial failure invisible to monitoring. Bound attempts and separate raw fallback from schema-valid output. Revalidate repaired fields and their source support, because a model can satisfy formatting by inventing missing information. The current section parser does not implement this complete proposed validation contract.

3.1.1. Which parser fixtures would make that contract reviewable?
Use a valid response, a missing section, repeated section headers, fenced JSON, a truncated output and a response with a valid shape but unsupported content. Specify which cases yield structured fields, flagged raw text or failure. Assert that each outcome remains observable. Structural fixtures test parsing; factual fixtures test evidence support, so passing one category must not be reported as success for both.
