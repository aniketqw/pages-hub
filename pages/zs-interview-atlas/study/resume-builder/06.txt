WHY THIS QUESTION MATTERS

CONTEXT
The resume lists a test total and a non-root image. The first is a claim about a test run; the second is a claim about process identity. This card teaches how to defend each without borrowing evidence from a different commit or environment.

TERMS
regression test: A controlled case that detects recurrence of a known failure.
test selection: The collected cases actually included by a command and its markers.
non-root: A process identity property that is only part of a deployment boundary.

MECHANISM
1. Read the repository trace’s test delta as reported history, then run a separate controlled offline environment against the pinned commit. Preserve the command, dependency versions and any exclusions.
2. Inspect what a test asserts: graph branch parity, source-location trust and shared limiter wiring cover different mechanisms. Passing them does not measure all future answer quality or production scale.
3. Read the Dockerfile’s USER declaration as one boundary. Runtime mounts, network permissions and deployed configuration determine other capabilities; no Docker execution is implied by source inspection.

FOLLOW-UP QUESTIONS AND ANSWERS

1. Why can the same test total mean something different on two commits?
A total counts collected cases under a command on a specific version. Some tests may have been added while others were removed, or the environment may collect different cases. Cite the commit and selection first. Then name a behavior covered by a test rather than using the total to imply broad quality.

1.1. How should you report the newest trace and the previous offline run?
Say the source trace reports 540 for the newest iteration. Say the earlier local suite passed 532 at the previous pinned commit. Keep any new focused run separate, with its exact selection. Those are three observations with different scope. None should be presented as new evidence of production latency or a deployed Docker runtime.

1.1.1. What makes a regression test useful for an interview bug story?
Start from a real observable failure. Write a small test that would fail for that reason. For a missing PDF title, assert the title text, not only that parsing finishes. For a structured provider response, assert the request and the parsed fields. Mention a revert check only if a record actually shows it.

2. Why is that only one part of the deployment boundary?
Process identity limits default permissions, but mounted files, capabilities, network access and application authorization still determine what can happen. A non-root process may read sensitive data it was given or send it through allowed egress. Inspect runtime configuration and negative cases before describing the container as a complete sandbox.

2.1. Does the current safety_scan inspect all fetched source for secrets?
No. The function scans paths, README and key_files; the new source_files collection is not passed through its content loop. It also returns findings rather than establishing a universal block before every generation. This is a concrete coverage limit to review, not a claim that a leak occurred in the tested run.

2.1.1. What focused improvement would address that source-evidence gap?
Scan the bounded source content that can enter the model bundle, define which findings block or redact it, and test that sensitive fixture text never reaches the fake provider. Preserve diagnostic location without copying usable secrets. That proposal needs a privacy policy and regression checks; the architecture review does not silently implement it in the project repository.

3. Why test branch visits instead of only checking the final document?
Two implementations can produce the same small fixture while taking different stages, omitting safety checks or making extra provider calls. Assert the expected visited node set and the excluded full_run stages for browser import. Then check the resulting document. That makes shared orchestration a tested behavior rather than an inference from similar output.

3.1. How can test collection order hide an import defect?
An earlier test can import and initialize a package in an order that avoids a circular dependency. A fresh CLI process may import the same modules in the failing order. Add a subprocess or fresh-interpreter import test for the supported entry points, rather than relying only on an already initialized pytest process.

3.1.1. Does passing those offline checks verify the source’s live tracing claim?
No. Offline fakes can verify parent-child trace construction, fallback and error isolation without posting to LangSmith. The repository trace separately reports a live run and nested trace verification. Attribute that report and state that this review did not spend provider quota or independently inspect its live backend.
