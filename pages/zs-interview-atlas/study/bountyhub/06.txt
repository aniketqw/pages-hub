FOLLOW-UP QUESTIONS AND ANSWERS

1. Why maintain a denormalized Mongo catalog?
It supports a dedicated text-search path while PostgreSQL handles relational writes and constraints. The tradeoff is sync lag and complexity, so justify it with measured query needs. “No matches” and “Mongo is unavailable” both trigger the PostgreSQL fallback in this service, but they mean different things operationally. Empty results may be a valid answer; a thrown Mongo error indicates dependency failure. I would preserve that distinction in metrics and response behavior so a slow fallback does not hide a broken catalog.

1.1. How would you distinguish empty search from Mongo failure?
Return an explicit result state from discovery, such as success-with-zero, success-with-results, or unavailable, rather than overloading null and empty. The caller can choose fallback for unavailable and perhaps for empty only if fallback semantics are intended. I would add counters for each outcome and compare sampled result IDs between stores. This makes a fallback measurable instead of an invisible branch.

1.1.1. Would fallback on every empty Mongo result be correct?
Not necessarily. Mongo may have stricter matching or lagging data, while PostgreSQL contains substring matching; a fallback can introduce results that contradict the primary search semantics. Product expectations should define whether this is acceptable. I would test query cases with zero, one, and multiple terms and label fallback-origin results in telemetry before changing behavior. The response should preserve which backend answered so a fallback does not silently alter relevance expectations. 2. How verify that claim?
Search producers, consumers, key schema, invalidation, and tests, then trace one write end to end. If absent, label it unverified rather than infer from Redis use. The repository comment says “full-text,” but the fallback uses case-insensitive `contains` over title and description; that is not PostgreSQL full-text search. A leading wildcard can also limit ordinary B-tree index use. I would inspect schema indexes and query plans before making a performance claim.

2.1. What index might help substring search?
A trigram GIN or GiST index can support many substring and similarity operators, but the exact Prisma-generated SQL and PostgreSQL operator class matter. A normal B-tree index generally will not accelerate arbitrary contains patterns. I would reproduce the generated query, add the candidate index in a disposable database, run EXPLAIN ANALYZE at realistic cardinality, and compare write cost as well as read latency.

2.1.1. How would you prevent an index from becoming a guess?
Start with observed query plans, representative data volume, and a target latency objective. Measure p50 and p95 before and after the index, plus insert/update overhead and index size. Keep the index only if it improves the workload that matters. I would also test cancellation and status filters, because a search index that speeds text matching may not eliminate sorting or count costs.

3. What is a fair comparison?
Use the same corpus and queries, judge recall/ranking, record p50/p95 and freshness, and include Mongo outage fallback. `skip` and `take` implement offset pagination, and the query performs a separate count. Deep pages can scan or discard many rows, while the total count can cost more than the page fetch. I would set maximum page size and consider cursor pagination if clients routinely go deep.

3.1. What consistency issue can cursor pagination improve?
A cursor based on a stable ordered key such as `(createdAt,id)` avoids many rows shifting between page requests when new records arrive at the front. It does not automatically give a frozen snapshot, and the cursor must include filters and sort direction. I would test inserts between pages and ensure no duplicates or omissions under the chosen contract. 3.1.1. Would you remove the total count from the response?
Only if the client experience can use next-page availability or an approximate total. Exact count across a large changing dataset can be expensive and may be inconsistent with the page query unless both share a snapshot. I would inspect product requirements, measure count latency independently, and consider a capped or asynchronously computed total rather than silently returning a misleading number.
