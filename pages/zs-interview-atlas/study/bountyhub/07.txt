QUESTION
What does the Docker Compose topology establish, and what can you honestly claim about failure behavior?

WHY THIS QUESTION MATTERS
Tests the implementation boundary, failure modes, and whether I can separate code evidence from assumptions.

CONTEXT
A Compose file describes intended local wiring, while runtime evidence comes from launching services and observing them under failure. Keep topology, readiness, security configuration, and recovery as distinct claims.

TERMS
health check: Configured probe used to decide whether a service appears ready.
replica lag: Delay between a primary write and its appearance on a replica.
fault injection: Deliberately cause dependency failure to observe behavior.

MECHANISM
1. Read declared service dependencies and distinguish `depends_on` from data consistency.
2. Inspect each health check and state exactly what that probe proves.
3. In an isolated stack, record a known write, interrupt one dependency, restore it, and verify data converges.
4. Review development credentials and mounts before discussing any shared deployment.

TECHNICAL EXPLANATION
`depends_on: service_healthy` gates startup on configured checks, but these probes are shallow. PostgreSQL replica health does not guarantee replay of a particular write; Mongo ping does not prove auth, indexes, or application query behavior. The config has development credentials and should not be treated as production hardening. Validation needs health semantics, migration/seed safety, restart behavior, backup/recovery, and fault injection. The honest boundary is “topology declared”; this audit did not run containers or measure availability. `depends_on: service_healthy` helps order startup but does not coordinate a database write with replica replay. Liveness should answer whether a process is stuck; readiness should answer whether it should receive traffic, and optional search degradation may not require restarting the API. Test failure and convergence separately: a process becoming healthy again does not prove Mongo has caught up. The Compose credentials are development values, not production secret management.

1. What does the health check not establish?

1.1. What would you assert in a readiness check?
Keep process liveness separate from dependency readiness. A readiness probe can verify the API can serve its intended traffic, while a deeper diagnostic can report database, Redis, and Mongo states without making every temporary dependency issue restart the container. I would avoid declaring the replica ready solely from `pg_isready`; a replication-lag check needs its own measurement.
