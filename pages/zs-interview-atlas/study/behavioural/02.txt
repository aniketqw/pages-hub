SELF-CHECK
If the client task can be solved with a fixed query, what should you recommend?
Recommend the simplest approach that meets agreed accuracy, maintainability, and review requirements. Compare it with an LLM only if a real requirement needs language flexibility, then measure the added cost and failure modes. The goal is a useful client outcome, not framework use.

FOLLOW-UP QUESTIONS AND ANSWERS

1. How would you turn a JD responsibility into a first project milestone?
I would translate a responsibility into a user decision and an observable acceptance criterion before choosing a framework. For example, if the work involves extracting information, define which fields must be correct, what evidence supports them, and what happens when confidence is low. Then build the smallest baseline that can be reviewed with a domain partner.

1.1. What would you do if the user asks for an LLM before defining the task?
I would ask for representative inputs, the decision they need to make, and the cost of an incorrect answer. A fixed query, rules, or search may be safer and cheaper. I would compare a baseline against the requested approach with the same acceptance criteria, then explain the result rather than arguing from preference.

1.1.1. How would you communicate that a simpler baseline is enough?
Show examples where it meets the agreed criteria, plus the edge cases it cannot handle and the cost of adding an LLM. If the baseline misses an important case, that becomes evidence for the next experiment. I would frame this as a decision from measured requirements, not a general claim that LLMs are unnecessary.

2. What makes the projects transferable to a ZS client workflow?
The transferable habits are evidence tracking, explicit validation, and communicating uncertainty; the projects do not prove client-domain delivery. I would first learn the business definitions and data constraints, then map a project pattern such as structured extraction or tool routing to a small workflow with a reviewer. The domain owner decides whether the output is useful.

2.1. How would you measure usefulness for an analyst?
Agree on a task-specific measure with the analyst: time saved only if quality stays within an accepted range, fewer missed fields, or faster review. Include a baseline and cases where the tool should abstain. I would not claim improvement until a pilot measures the workflow and checks for downstream correction cost.

2.1.1. What would you do if the model score improves but analyst trust falls?
Investigate where the score and experience diverge: wrong but confident answers, slow review, poor provenance, or a mismatch in the metric. I would inspect representative cases with analysts and change the evidence display or scope before expanding. Aggregate accuracy alone does not establish adoption or safe decision support.

3.1.1. What would you ask a domain expert first?
I would ask what decision the workflow supports, how key fields are defined, what exceptions matter, and which errors are most costly.
