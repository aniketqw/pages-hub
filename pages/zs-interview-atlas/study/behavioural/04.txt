SELF-CHECK
If labels come from the same threshold rules used as features, what can the evaluation establish?
It can show that a model reproduces those rules, not that it identifies real workload behavior. I would seek an independent source of truth or describe the work as rule emulation, and avoid presenting test accuracy as external validity.

FOLLOW-UP QUESTIONS AND ANSWERS

1. What labels would a workload classifier need before training?
It needs an independent source of workload truth. If labels are generated from the same traffic thresholds used as features or rules, the model may only reproduce the labeling heuristic. I would define the target, label provenance, and uncertain cases before training. The accessible work map says no trained model was built.

1.1. How would you split the labeled data?
Group related flows by host, session, or time so near-identical observations do not appear in train and test. A temporal holdout can expose behavior changes. I would compare with a simple heuristic baseline and report per-class errors, not only one aggregate accuracy number.

1.1.1. What if some workload labels are unreliable?
Keep an uncertain category or review queue rather than forcing a class. Measure how performance changes when uncertain labels are excluded or adjudicated. If label quality is weak, I would improve the collection process before tuning model architecture; otherwise training can make the system confidently reproduce bad labels.

2. How would you detect when a traffic signature changes?
A behavior inferred from traffic can drift when software, routing, or usage patterns change. I would log feature distributions and prediction confidence by time and source, then compare them with verified outcomes. A change detector can prompt revalidation, but it does not identify the cause by itself. No such trained detector is established by this project record.

2.1. Would a distribution shift automatically mean the model is wrong?
Not necessarily. A shift is a signal to inspect, not proof of degraded decisions. Evaluate labeled recent cases and compare decision costs; a shift can be harmless or can expose a missing class. I would define the escalation threshold from validation performance and use review rather than automatic retraining.

2.1.1. How would you handle a new, unseen workload?

3. What separates an action recommendation from an executed control loop?
An action path needs verified inputs, a policy that permits the action, an actuator, outcome observation, and a rollback or safe-stop plan. A table mapping telemetry to actions only expresses a design. I would identify what I personally implemented and tested, and avoid saying the system autonomously changed hardware.

3.1. What checks should precede an automated network action?
Validate the signal, target, permissions, blast radius, and expected effect; require approval for high-impact changes; then use a staged rollout with monitoring and rollback. These are design controls, not claims about the confidential project. The action should be idempotent or guarded against repeated execution.

3.1.1. How would you prove the action helped?
Compare observed outcomes with a baseline or controlled rollout, track unintended effects, and retain a trace from input signal to action and result. If the action was only proposed, say evaluation remains future work. Do not convert a plausible operational metric into a measured result.
