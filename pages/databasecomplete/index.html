Question 1 · Worked example

A shop takes ₹600 and later returns ₹150. What should its payment history show?

What is happening? A capture is money collected from a customer. A refund sends some of that money back. The ledger is the permanent record of those events. Here, net paid means money collected minus money returned for this one payment.

Think before the walkthrough. Write down what you would need to answer “How much had the customer paid at 10:30?” If you only have today’s total, which fact is missing?

  1. Start at ₹0. The capture adds ₹600. Record a capture entry for ₹600 with the payment ID and event time.
  2. Record the refund as a new entry for ₹150 linked to the same payment. The original capture still tells you how much was collected.
  3. Read through the cutoff you care about. Before the refund, the customer had paid ₹600. After it, the net is ₹600 − ₹150 = ₹450.

Why can this get harder? One mutable total of ₹450 hides how you got there. A production ledger also needs balanced postings across its accounts and a way to reject duplicate events.

10:00Capture +₹600 → net paid ₹600
LaterRefund −₹150 → net paid ₹450

Why it works. A payment ID identifies the business request. An event ID identifies one capture or refund for that payment. A posting is one account’s side of an event. Sum payment events for the customer view and sum postings for account balances. Summing all postings for a balanced event gives zero.

Concepts behind the example. An entity is a kind of record. A candidate key could identify a record on its own. A foreign key links to another record. A dependency such as account ID determining currency means that finding the ID fixes the currency. 1NF avoids repeating groups in one field. 2NF removes partial key dependencies, 3NF addresses dependencies through non-key facts, and BCNF requires every determinant of a nontrivial dependency to be a superkey. These rules address data duplication, while the balance invariant addresses correctness of a posting.

Concepts to learn

Entities and relationships define what exists and how records link. Candidate and foreign keys identify rows and protect relationships. Functional dependencies explain why 1NF, 2NF, 3NF and BCNF separate facts that change independently. An invariant is a rule that must stay true after every committed operation.

Solution, step by step

  1. Read the two ER diagrams below. The starter model stores one mutable total. The revised model separates payment identity, provider attempts, posted business events and each event’s account effects. A failed attempt may exist with no journal entry.
  2. Assign stable primary keys. Use foreign keys for those relationships. Scope unique external event references by provider and merchant, or by the provider’s actual uniqueness contract.
  3. A separate flat report keyed by (payment_id, attempt_no, posting_no) can repeat the same account currency across rows. If one copy is corrected and another is missed, reports disagree. Question 1 · Worked example

One payment has two refunds and two settlement attempts. What happens if you join both lists before adding the refunds?

What is happening? A join pairs records that share a key. The payment ID is the key here. A settlement attempt is a separate record of an attempt to move funds to the merchant.

Think before the walkthrough. Before adding any amounts, predict how many output rows one refund will appear in. Draw a line from it to every matching settlement.

  1. Start with refunds R1 = ₹50 and R2 = ₹100. Settlement attempts are S1 and S2. All four records use the same payment ID.
  2. Match each refund to both attempts. The pairs are R1–S1, R1–S2, R2–S1 and R2–S2. A sum over those rows gives ₹300.
  3. First add the refunds in their own table. Keep one refund summary row of ₹150 for the payment. Summarize settlements separately if needed. Join the two summaries.

Why can this get harder? The table looks valid even when its totals are wrong. Before you add amounts, ask what a single output row represents.

Raw joinR1 and R2 each match S1 and S2
Group then joinR1 ₹50 + R2 ₹100 = ₹150

Why it works. A join combines matching rows. A one-to-many join can repeat a parent row. Joining two independent child lists creates every matching pair. Aggregation is safe only after you know what one row represents.

Concepts behind the example. SQL commonly keeps duplicate rows. NULL marks unknown or absent data. Grouping changes row grain, a window preserves it, and keyset paging resumes after an ordered tuple. An ORM maps records to objects, but its convenience can hide extra database calls.

Concepts to learn

SQL operates on sets or bags of rows. A join changes row count. NULL means missing or unknown. Grouping combines rows. A window computes across related rows while preserving their detail. An ORM can make one network request per parent row even when the query looks simple.

Question 1 · Worked example

Why might reading the same 60 data pages twice require fewer disk reads the second time?

What is happening? A database reads data in groups of bytes called pages. A buffer pool is memory that keeps recently used pages available. A scan walks through part or all of the stored data.

Think before the walkthrough. Mark a page as “already in memory” or “must fetch.” How many storage reads change if the second run requests exactly the same pages?

  1. Assume none of the 60 pages are in the buffer pool. For this example, the first scan must fetch all 60 from storage.
  2. Assume the pool has room for all 60 and no other workload replaces them. The next scan finds all 60 in memory. It still examines their rows, but it needs zero storage reads for those pages.
  3. Now assume only 20 requested pages remain cached when the second scan starts and all 20 survive until used. It needs 40 storage reads.

Why can this get harder? Fewer storage reads can make a benchmark faster even when the SQL and plan stay the same. Record cache conditions before comparing results.

First scan60 pages absent → 60 fetches
Warm scan60 pages retained → zero fetches in the model

Why it works. A page is a unit of access. A database buffer hit can avoid fetching it through the storage path. A buffer miss may still be served by the operating system cache. Keep these layers separate when reading counters.

Concepts behind the example. Row layout puts one record’s fields together. Column layout puts a field’s values together. Compaction rewrites sorted runs. Measure write amplification as storage bytes written divided by logical bytes written, under a named workload.

Concepts to learn

Pages are units of I/O. The buffer pool reuses pages. Row layout groups fields from one record. Column layout groups values of a field. B-trees organize ordered keys. LSM trees append to sorted runs and later compact them. Write amplification measures physical bytes written per logical byte.

Question 1 · Worked example

A cashier wants the five newest payments for one shop. How can an index reduce the work?

What is happening? An index is an extra structure that helps a database find records. The planner chooses an execution path before the query runs. We will compare the work needed for two paths.

Think before the walkthrough. Ask whether the query needs five matches or nearly every match. Under which request can it stop early?

  1. Without a useful index, a simple path reads the payments, keeps rows for that shop and finds the newest five among them.
  2. An index sorted by shop ID and newest time first puts the shop’s recent entries next to each other. Seek to the shop, read matching entries in order and stop once five eligible rows are found.
  3. Change the request to export every payment for a shop that owns most rows. The early stop is gone. Scanning the table in order can be cheaper than fetching many rows through an index.

Why can this get harder? The same index can help one read and add work to every affected insert. Query shape, matching row counts and write workload all matter.

Scan pathRead candidates and select top five

Question 1 · Worked example

What is happening? Two requests can run at the same time. Each can see the old value before either writes. A transaction groups operations that should succeed or fail together.

Think before the walkthrough. Pause both requests right after their reads. If neither writes until both read, how many refunds can each clerk think are safe?

Question 1 · Worked example

An agent earns points for two citations. Can it score well while finding only one piece of evidence?

What is happening? A policy selects actions. A reward is a score used to train or compare the policy. A verifier checks whether the result satisfies a rule.

Think before the walkthrough. Count citations, then count independent sources that actually support the claim. What happens when those counts differ?

  1. Give one point per citation. The agent finds an original article and a mirror that copied it. The naive score gives two points.
  2. Track where each claim came from. Both citations share one origin, so the verifier counts one independent source.
  3. Require two independent sources that support the claim. Test mirrors and copied text on cases the policy did not see during training.

Why can this get harder? A policy learns to increase the score you give it. If the score overlooks a shortcut, higher reward can coexist with worse work.

Naive rewardTwo mirrors count as two links
VerifierThey count as one supporting origin

Why it works. A policy chooses actions. A verifier checks the outcome. Reward hacking occurs when a policy scores well through a shortcut that fails the real task.

Concepts behind the example. An episode is one run. Observations are available state and actions are choices. Termination ends the run. Credit assignment connects the outcome to earlier choices. RLHF uses human-derived feedback in training. GRPO uses relative signals within groups. DPO learns from preference pairs.

Concepts to learn

Define an episode, observation, policy, action, reward and termination. Credit assignment connects a final outcome to prior choices. DPO uses preferences.
